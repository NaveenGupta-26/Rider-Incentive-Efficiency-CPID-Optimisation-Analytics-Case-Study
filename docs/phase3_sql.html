Q1Baseline Delivery Rate
What Does Each Rider Normally
Deliver Without Any Bonus?
Foundation query — must run before anything else. This is the counterfactual.

Before we can measure what a bonus adds, we need to know what a rider delivers without one. This query takes only weeks where no incentive was active and at least 4 days were worked — giving us a clean, stable baseline per rider, grouped by how long they've been on the platform.

This is the denominator of the entire CPID framework. If this number is wrong, everything downstream is wrong. So we build it first, carefully.

The query
WITH no_inc AS ( SELECT tenure_band, rider_id, AVG(deliveries_completed) AS avg_baseline_deliveries FROM shifts WHERE incentive_type = 'none' AND days_active >= 4 -- exclude low-activity weeks that skew baseline GROUP BY tenure_band, rider_id ) SELECT tenure_band, COUNT(rider_id) AS riders_in_band, ROUND(AVG(avg_baseline_deliveries),1) AS avg_weekly_baseline, ROUND(MIN(avg_baseline_deliveries),1) AS min_weekly_baseline, ROUND(MAX(avg_baseline_deliveries),1) AS max_weekly_baseline FROM no_inc GROUP BY tenure_band ORDER BY CASE tenure_band WHEN '0-2mo' THEN 1 WHEN '2-6mo' THEN 2 WHEN '6-12mo' THEN 3 ELSE 4 END

Baseline deliveries are remarkably consistent across tenure bands — all hovering around 92–95 per week. All tenure bands start from a similar baseline. Any difference in how much a bonus moves them above that baseline is a genuine elasticity difference, not a volume effect.

Q2CPID by Incentive Type — Core DiD Query
Which Bonus Type Generates
the Most Incremental Deliveries Per Rupee?
The main hypothesis 1 test. Difference-in-Differences approach.

This is the central query of the entire project. For each incentive type, we calculate what riders delivered in incentive weeks versus what they would have delivered at baseline — then divide total bonus spend by those incremental deliveries. The result is CPID: the true cost of each extra delivery the bonus actually generated.

The DiD approach here is: compare each rider to their own baseline (not a city average, not a platform average — their personal counterfactual from Q1). This removes confounders like city density and rider skill from the comparison.

The query
WITH baseline AS ( SELECT rider_id, AVG(deliveries_completed) AS avg_baseline FROM shifts WHERE incentive_type = 'none' AND days_active >= 4 GROUP BY rider_id ), incentive_weeks AS ( SELECT s.rider_id, s.incentive_type, SUM(s.deliveries_completed) AS total_deliveries, SUM(s.deliveries_completed - b.avg_baseline) AS incr_deliveries, SUM(s.incentive_pay) AS total_incentive_pay FROM shifts s JOIN baseline b ON b.rider_id = s.rider_id WHERE s.incentive_type != 'none' GROUP BY s.rider_id, s.incentive_type ) SELECT incentive_type, COUNT(rider_id) AS riders, ROUND(SUM(total_incentive_pay) / NULLIF(SUM(GREATEST(incr_deliveries,0)),0), 1) AS cpid_rs, ROUND(SUM(GREATEST(incr_deliveries,0))*100.0/ NULLIF(SUM(total_deliveries),0), 1) AS pct_deliveries_incremental FROM incentive_weeks GROUP BY incentive_type ORDER BY cpid_rs

H1 verdict — partially confirmed, with a twist

Streak bonus beats flat on CPID (₹73.2 vs ₹92.1 — a 20.5% difference), which confirms H1's direction. But surge top-up is actually the most efficient of all three at ₹57.9. The reason: surge bonuses pay per online hour — they move supply at Stage 1 of the funnel (riders coming online) rather than Stage 3 (pushing for extra completions). Since coming online at all is the biggest supply bottleneck, this has the highest marginal impact.

The important nuance: flat per-order bonus has an ROI below 1.0 in Q8, meaning the platform is spending more on the bonus than the incremental deliveries are worth in revenue. Streak and surge both generate positive ROI.

What NULLIF and GREATEST are doing here — and why they matter

GREATEST(incr_deliveries, 0) prevents negative incrementality from dragging down the average — some riders deliver slightly less in incentive weeks due to random variance, not because the bonus harmed them. NULLIF prevents division-by-zero errors when a rider has no incremental deliveries at all. Both are defensive SQL patterns that a senior analyst should write by default.

Q3CPID by Tenure Band × Incentive Type
Who Responds Best
to Which Bonus, and When?
H2 deep dive — the segmentation that makes recommendations actionable.

Q2 tells you which incentive type is most efficient overall. Q3 tells you for which riders. This is the query that turns a finding into a strategy. If streak bonuses are efficient for 2–6 month riders but not for 12+ month veterans, the recommendation is not "replace all flat bonuses with streak bonuses" — it's "replace flat bonuses with streak bonuses for 2–6 month riders, and something else for veterans."

The query
WITH baseline AS ( SELECT rider_id, AVG(deliveries_completed) AS avg_baseline FROM shifts WHERE incentive_type = 'none' AND days_active >= 4 GROUP BY rider_id ) SELECT s.tenure_band, s.incentive_type, COUNT(DISTINCT s.rider_id) AS riders, ROUND(AVG(s.deliveries_completed - b.avg_baseline),2) AS avg_incr_per_week, ROUND(AVG(s.incentive_pay) / NULLIF(AVG(GREATEST(s.deliveries_completed - b.avg_baseline, 0.01)),0), 1) AS cpid_rs FROM shifts s JOIN baseline b ON b.rider_id = s.rider_id WHERE s.incentive_type != 'none' GROUP BY s.tenure_band, s.incentive_type ORDER BY tenure_band_order, cpid_rs

For 12+ month veterans, flat bonuses are producing only 5.30 incremental deliveries per week on average — these are genuinely always-on riders. The recommendation is not to cut their pay but to shift them to surge top-ups, which at least reward their online hours rather than trying to squeeze extra deliveries from people already at capacity.

Q4CPID by City Tier
Does the Same Bonus
Work Harder in Smaller Cities?
H3 test — geographic efficiency of incentive spend.

The same ₹100 bonus sent to a rider in Mumbai and a rider in Bhopal does not buy the same result. Mumbai has thousands of riders already at capacity during peak hours. Bhopal has fewer riders and more room for supply to respond to incentives. This query measures that gap — and it turns out to be large enough to completely change how the incentive budget should be allocated geographically.

The query
WITH baseline AS ( SELECT rider_id, city_tier, AVG(deliveries_completed) AS avg_baseline FROM shifts WHERE incentive_type = 'none' AND days_active >= 4 GROUP BY rider_id, city_tier ), weekly AS ( SELECT s.city_tier, s.incentive_type, SUM(GREATEST(s.deliveries_completed - b.avg_baseline, 0)) AS incr_del, SUM(s.incentive_pay) AS spend FROM shifts s JOIN baseline b ON b.rider_id = s.rider_id WHERE s.incentive_type != 'none' GROUP BY s.city_tier, s.incentive_type ) SELECT city_tier, ROUND(SUM(incr_del), 0) AS total_incr_deliveries, ROUND(SUM(spend), 0) AS total_spend_rs, ROUND(SUM(spend)/NULLIF(SUM(incr_del),0), 1) AS cpid_rs, ROUND(SUM(spend)*100.0/ (SELECT SUM(spend) FROM weekly), 1) AS pct_of_total_spend FROM weekly GROUP BY city_tier ORDER BY cpid_rs

H3 confirmed — and the numbers are starker than expected

Tier-1 cities consume 33.8% of the total incentive budget but generate only 6.3% of all incremental deliveries across all tiers. Tier-2 cities use 38.5% of the budget and generate 46.4% of incremental deliveries. Tier-3 uses 27.7% and generates 45.1%. The Tier-1 vs Tier-2 CPID gap is 2.53× — well above the 2× threshold we set in H3. This is the most financially impactful finding in the project. Reallocating even 10% of the Tier-1 budget to Tier-2 and Tier-3 cities would generate substantially more incremental deliveries for the same spend.

Important nuance on Tier-1 — this doesn't mean pull out entirely

Tier-1 metros drive the bulk of GMV and order volume. Supply must be maintained there even if incentives are less efficient. The recommendation is not "stop incentivising Tier-1 riders" — it's "shift Tier-1 incentives toward surge top-ups that reward online presence rather than extra deliveries, and redirect discretionary incentive budget toward Tier-2/3 where marginal spend creates more supply."

Q5Incentive Cliff Effect
What Happens the Week
After the Bonus Ends?
Supply risk check — measuring dependency vs habit formation.

When a bonus ends, do riders maintain their higher activity level, or do they drop back? A small drop is normal. A large drop means the incentive created dependency — riders have mentally reset their earnings expectations upward, and now the non-bonus week feels like a pay cut even though it isn't. This is both a supply risk and, critically, a rider welfare risk — sudden perceived income drops cause stress and exits.

The query
SELECT cliff_week_flag, COUNT(*) AS shift_weeks, ROUND(AVG(online_hours),1) AS avg_online_hours, ROUND(AVG(deliveries_completed),1) AS avg_deliveries, ROUND(AVG(total_weekly_earnings),0) AS avg_weekly_earnings_rs FROM shifts GROUP BY cliff_week_flag ORDER BY cliff_week_flag

The cliff is manageable — but the earnings drop is the real issue

Online hours drop only 4.1% in cliff weeks — that's minor. But deliveries drop 10.5% and earnings drop 26.4%. The earnings drop is large because cliff weeks have no incentive pay at all (by definition). This is a rider welfare signal: the week after a high-incentive period, a rider can feel a significant income dip even if they're working just as hard. The 2–6 month band shows the biggest cliff drop (−8.8% in hours) — ironically the group that responds best to incentives is also most susceptible to the cliff. The design implication: avoid creating incentive calendars that have sharp on/off switches. Gradual incentive tapering is better for rider stability than binary on/off scheduling.

Q6Streak Completion Rate
Do Riders Actually
Complete the Streak?
Streak validity check — if nobody completes the streak, the psychology argument breaks down.

The case for streak bonuses rests on one behavioural claim: riders who are close to a threshold will push to hit it, generating incremental deliveries. But this only works if riders are actually completing streaks. If completion rates are low, the bonus is being earned by high-volume riders who'd hit the threshold anyway, not by the marginal rider being pulled to do 3 more deliveries.

The query
-- Streak = 10 deliveries per day. We proxy at weekly level: -- avg_daily_deliveries = deliveries_completed / days_active -- If avg daily >= 10, rider is consistently hitting the daily streak threshold WITH daily_proxy AS ( SELECT tenure_band, rider_id, week_start, deliveries_completed, days_active, incentive_pay, ROUND(deliveries_completed::FLOAT / days_active, 1) AS avg_daily_del, CASE WHEN deliveries_completed / days_active >= 10 THEN 1 ELSE 0 END AS hit_daily_streak FROM shifts WHERE incentive_type = 'streak_bonus' ) SELECT tenure_band, COUNT(*) AS streak_weeks, ROUND(AVG(avg_daily_del), 1) AS avg_daily_deliveries, ROUND(100.0*SUM(hit_daily_streak)/COUNT(*), 1) AS pct_hitting_streak, ROUND(AVG(incentive_pay), 0) AS avg_incentive_earned_rs FROM daily_proxy GROUP BY tenure_band ORDER BY tenure_band_order

Honest finding — what this query revealed about our dataset

Streak completion rates are uniformly high (85–91%) because our riders average 17–21 deliveries per day — well above the 10-delivery streak threshold. This is realistic: the documented 10-delivery streak is a daily target, and full-time riders in our dataset (which skews toward full-time, per the source data) comfortably exceed it. The streak bonus is paying out reliably, which is good for rider earnings. The CPID advantage from streaks vs flat comes not from completion psychology at this threshold level — it comes from riders doing 2–4 extra deliveries to clear the next streak threshold. A real-world platform would calibrate the streak threshold to sit just above the rider's median daily delivery count to maximise the psychological pull. This is a design recommendation we carry into Phase 7.

Q7Time of Day × Incentive Type
When Does the Surge Bonus
Actually Need to Run?
Operational efficiency — matching incentive timing to demand peaks.

Surge top-up incentives make most sense during demand peaks — when more riders need to be online but supply is naturally thin. Running them during the afternoon lull (when fewer orders are placed anyway) is wasteful. This query maps order volume by hour of day and by incentive type to identify whether surge bonuses are being deployed when they're actually needed.

The query
SELECT CASE WHEN hour_of_day BETWEEN 8 AND 10 THEN '08-11 Morning peak' WHEN hour_of_day BETWEEN 11 AND 13 THEN '11-14 Lunch peak' WHEN hour_of_day BETWEEN 14 AND 17 THEN '14-18 Afternoon lull' WHEN hour_of_day BETWEEN 18 AND 22 THEN '18-23 Dinner peak' ELSE 'Other' END AS time_slot, incentive_type, COUNT(order_id) AS order_count, ROUND(AVG(order_value),0) AS avg_order_value_rs, ROUND(AVG(distance_km),2) AS avg_distance_km FROM orders WHERE status = 'completed' GROUP BY time_slot, incentive_type ORDER BY time_slot, order_count DESC

Dinner peak (18–23) is the highest-volume slot by far — 20,230 orders completed in control weeks. Q8Net Unit Economics Per Delivery
Which Bonus Actually
Makes the Platform Money?
The P&L query — translates CPID into revenue vs cost at the business level.

CPID is a cost metric. This query is the business translation: for each incentive type, does the revenue generated by incremental deliveries actually exceed the cost of the incentives that drove them? This is what a CFO or Head of Operations cares about. An incentive with a great CPID that still loses money is not a good incentive. An incentive with a high CPID that generates strong ROI is still worth running.

We use a 17% take rate on ₹435 AOV = ₹74 revenue per delivery, sourced from Swiggy's documented commission range of 15–25%.

The query
WITH baseline AS ( SELECT rider_id, AVG(deliveries_completed) AS avg_baseline FROM shifts WHERE incentive_type = 'none' AND days_active >= 4 GROUP BY rider_id ), econ AS ( SELECT s.incentive_type, SUM(GREATEST(s.deliveries_completed - b.avg_baseline, 0)) AS incr_deliveries, SUM(s.incentive_pay) AS total_incentive_spend FROM shifts s JOIN baseline b ON b.rider_id = s.rider_id WHERE s.incentive_type != 'none' GROUP BY s.incentive_type ) SELECT incentive_type, ROUND(incr_deliveries, 0) AS incr_deliveries, ROUND(total_incentive_spend, 0) AS incentive_spend_rs, ROUND(incr_deliveries * 74, 0) AS incr_revenue_rs, -- ₹435 AOV × 17% take rate ROUND((incr_deliveries * 74) / NULLIF(total_incentive_spend, 0), 2) AS incentive_roi -- revenue / spend FROM econ ORDER BY incentive_roi DESC

The most important single number in this project

Flat per-order incentives have an ROI of 0.98× — below 1.0. That means for every rupee spent on flat bonuses, the platform recovers only ₹0.98 in revenue from the extra deliveries those bonuses generated. The flat bonus structure, which is the dominant incentive type across the industry right now, is marginally loss-making when measured correctly. Streak bonuses are profitable at 1.17×. Surge top-ups are the most profitable at 1.50×.

Critically — and this is the rider-first point — none of this is achieved by cutting rider pay. It's achieved by changing the structure of the same budget so it creates more incremental deliveries per rupee. Riders earn as much or more. The platform recovers its costs. That's what a well-designed incentive framework looks like.
